# グローバルルール

## Language
- ユーザーへの説明、確認、要約は常に日本語で行う。
- 英語のエラーメッセージを提示する場合は、意味を日本語で短く説明する。

## Safety
- ファイルやディレクトリの削除、大規模置換、依存関係の追加または削除、DBマイグレーションなど、破壊的または広範囲に影響する操作は、事前に日本語で以下を説明して確認する。
  - 何をするか
  - 影響範囲
  - 元に戻す方法
- `.env`、秘密鍵、トークン、認証情報、または本番用と明示された設定ファイルは、ユーザーの許可なく閲覧、変更、内容の出力をしない。

## Workflow
- 影響が広い変更では、変更前に状況と作業方針を短く共有する。
- 変更は常に最小差分で行う。不要なリファクタリングはしない。
- 既存の命名規則、コードスタイル、ディレクトリ構成を優先する。
- 指示が曖昧な場合は、推測で危険な変更をせず、選択肢を日本語で示す。

## Skills
- プロジェクトまたはユーザースコープで利用可能な Skill から、依頼に必要な最小限の組み合わせを選ぶ。
- 該当する Skill を作業前に読み、その手順に従う。使用する Skill 名と理由は日本語で短く説明する。

## Commands
- 読み取り専用で挙動が明確なコマンドは、事前確認なしで実行してよい。
- 一見して挙動がわかりにくいスクリプト実行時は、主要な引数や処理内容も日本語で短く添える。
- プロジェクト内に定義された正式な test / lint / format コマンドを優先して使う。
- 既存の方法で対応できる場合は、新しい依存関係、ツール、コマンド体系を導入しない。

## Testing
- 変更に最も近い範囲のテストから実行する。
- テストやlintが失敗した場合は、失敗内容と考えられる原因を日本語で要約する。
- テストが未実施の場合は、その理由を明示する。

## Editing policy
- コメントやドキュメントは、必要なときだけ追加する。
- 意味が自明でない一文字変数や過剰な抽象化を避け、可読性を優先する。
- 既存ファイルの全面書き換えは避ける。

## Git
- 明示的に依頼されない限り commit / push / branch作成 は行わない。
- 変更内容は、最後に日本語で要点を簡潔にまとめる。
